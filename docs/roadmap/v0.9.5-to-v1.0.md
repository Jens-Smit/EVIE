# EVIE – Entwicklungs-Roadmap v0.9.5 → v1.0

> **Status:** In Arbeit  
> **Branch:** `v0.9.5`  
> **Ziel:** Stabilisierung der Kernarchitektur vor neuen Features  

---

## 🎯 **Ziele dieser Roadmap**

1. **Architektur einfrieren** (Phase 0): Keine neuen großen Features, bis die vorhandenen Kernkomponenten stabil sind.
2. **Security First**: Absolute Priorität für Secret Management, Tenant-Isolation und Security Hardening.
3. **Multi-Tenant-Fähigkeit**: Jede Komponente muss User/Tenant-Scoping unterstützen.
4. **Produktionsreife**: Async Runtime, Scheduler, Messenger und Observability für den produktiven Einsatz.
5. **Skalierbarkeit**: Vorbereitung für Enterprise-Nutzung mit Human-in-the-Loop und Audit-System.

## 🔴 **Phase 1 – Security Hardening** *(Absolute Priorität)*

### 1️⃣ **Secret Vault**

#### **Encryption-Upgrade**
- [ ] `AES-256-CBC` entfernen
- [ ] `AES-256-GCM` implementieren
- [ ] Authentication Tag speichern
- [ ] Encryption Version speichern
- [ ] Key Version speichern
- [ ] Encryption Service versionieren

**Ziel-Entity:**
```php
UserSecret
├── encryptedValue
├── encryptionVersion  // z.B. "AES-256-GCM-v1"
├── keyVersion          // z.B. "KEY_V2"
├── createdAt
└── updatedAt
```

#### **Secret Key Management**
- [ ] Master Key **ausschließlich** aus Environment/Secret Store (nie in DB!)
- [ ] Key Rotation vorbereiten
- [ ] Alte Keys weiterhin entschlüsseln können (Backward Compatibility)
- [ ] Re-Encryption-Mechanismus für Key Rotation
- [ ] Key Versioning (z.B. `KEY_V1`, `KEY_V2`, `KEY_V3`)

#### **Secret Leakage verhindern**
**Zu durchsuchende Pfade:**
- [ ] `src/`
- [ ] `tests/`
- [ ] `var/log/`
- [ ] Messenger (Nachrichteninhalte)
- [ ] Exceptions (Fehlermeldungen)
- [ ] Doctrine (Entity-Dumps)
- [ ] LLM (Prompt-Injection, Logs)
- [ ] Tools (Debug-Ausgaben)

**Zu prüfende Anti-Patterns:**
- [ ] API-Key Logging
- [ ] Secret Logging
- [ ] Request Logging mit Credentials
- [ ] Exception mit API-Key
- [ ] LLM Prompt mit Secret
- [ ] Debug Toolbar Secret Exposure
- [ ] Symfony Profiler Secret Exposure

## 🔴 **Phase 2 – Multi-Tenant Security** *(Strenge Isolation)*

### **Conversation**
- [ ] Jede Methode muss `User`/`Tenant` berücksichtigen
  - ❌ `getConversation($conversationId)`
  - ✅ `getConversation(User $user, ConversationId $id)`
- [ ] `getLastMessage()` mit User Scope
- [ ] `getFirstMessage()` mit User Scope
- [ ] `countMessages()` mit User Scope
- [ ] `conversationExists()` mit User Scope
- [ ] `deleteConversation()` mit User Scope
- [ ] `getConversation()` mit User Scope
- [ ] Conversation-ID auf **UUID/ULID** umstellen
- [ ] DB Unique Constraints prüfen (Tenant + ConversationID)
- [ ] Foreign Keys prüfen (Tenant-Referenz)

### **Scheduled Tasks**
- [ ] Jeder Task gehört eindeutig einem `User`/`Tenant`
- [ ] Repository Queries **immer scoped** (z.B. `->where('tenant = :tenant')`)
- [ ] Task-ID darf **keinen Fremdzugriff** ermöglichen
- [ ] `cancel()` nur durch Besitzer
- [ ] `delete()` nur durch Besitzer
- [ ] `execute()` nur durch autorisierten Worker
- [ ] Result ebenfalls User/Tenant scoped

### **Agent History**
- [ ] User Scope
- [ ] Tenant Scope
- [ ] Conversation Scope
- [ ] Parent Message Scope

### **Zugriffstests**
- [ ] Cross-Tenant Tests (User A → Conversation B von User B = **DENY**)
- [ ] IDOR-Tests (Insecure Direct Object Reference)

### **Retry-Mechanismus**
- [ ] Retry Policy (Wann wird retried?)

- [ ] Exponential Backoff (z.B. 1s, 2s, 4s)
- [ ] Dead Letter Queue (Für permanente Fehler)

- [ ] Retryable Errors (Welche Fehler dürfen retried werden?)

### **Idempotency** *(Sehr wichtig!)*
- [ ] **Ein Job darf nicht zweimal dieselbe Aktion ausführen!**
  - ❌ Beispiel: `Job retry → Invoice twice sent`

- [ ] Tool-level Idempotency (Tools selbst müssen idempotent sein)
- [ ] Transaction Boundaries (DB-Transaktionen für Atomarität)

## 🟡 **Phase 14 – SecurityGuard 2.0** *(Policy Engine)*

### **Flow:**
```
Tool Request       // z.B. "E-Mail löschen"
     ↓
Risk Analyzer     // Risiko bewerten (z.B. "high")
     ↓
Policy Engine     // Regel prüfen (z.B. "Delete Email → ASK")
     ↓
┌─────┼──────┐
│     │      │
ALLOW  ASK   DENY
```

### **Beispiel-Policies:**
| Aktion          | Entscheidung | Begründung                          |
|-----------------|--------------|------------------------------------|
| Read Email      | ALLOW        | Lesen ist sicher                   |
| Send Email      | ASK          | Bestätigung erforderlich            |
| Delete Email    | ASK          | Löschen ist kritisch               |
| Delete Database | DENY         | Zu gefährlich für automatische Ausführung |
| Execute Shell   | ASK / DENY   | Abhängig von Kontext               |
| Transfer Money  | ASK          | Finanztransaktionen immer bestätigen |
